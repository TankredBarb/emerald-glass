Это исходный снимок ревью. Последующие исправления, результаты регрессий и
исследование ресайза описаны в [REVIEW_FIXES.md](REVIEW_FIXES.md).

Проверены собственная декорация, CPU-материал, общий GLSL, KCM, оба вида
предпросмотра, интеграционные изменения vendored KWin effect, установщик,
CMake, тесты и документация. Исходники реализации в ходе ревью не изменялись.
Временные проверочные программы находятся в `/tmp/emerald-full-review`.

P1 — исправить до первого выпуска; P2 — функциональный дефект, исправить в

симптом без доказанной причины вынесен отдельно от установленных ошибок кода.

## 1. P1: Liquid Glass теряет alpha кэшированного фона

Место: [preview/glass.frag](../preview/glass.frag), строки 71–73, 243–249,
312–317.

Ветка без LG сохраняет RGBA результата Kawase. Ветка с LG берёт только RGB
premultiplied-текстуры, использует его как обычный цвет и выдаёт alpha,
равную покрытию рамки. Недостающая часть кэша становится непрозрачным тёмным
вкладом. Это тот же класс ошибки, для которого уже есть исправление и тест
стэкинга в ветке `opticsDisabled`.

Воспроизведено настоящим production GLSL через EGL/llvmpipe. Один и тот же
цвет фона `(0.3, 0.55, 0.25)` подан с разным premultiplied-покрытием.
Opacity 20%, Tint 0%, освещение и адаптация выключены, измеряется плоская
середина заголовка:

| Alpha кэша | Результат RGBA, 8 бит |
| --- | --- |
| 1.00 | 72, 124, 63, 255 |
| 0.75 | 57, 96, 50, 255 |
| 0.00 | 11, 12, 12, 255 |

Это доказывает неправильную обработку частично заполненного кэша в LG.
Частоту появления такого кэша в реальном compositor эта проверка не измеряет.
Не следует смешивать этот дефект с ожидаемым влиянием выбранного цвета и
Base Opacity при наложении полноценных материалов.

Исправление должно согласовать передачу света, покрытие материала и alpha
фона, сохранив исключение фона при Opacity 100% и запрет обхода blur через
резкий второй sampler. Тест частичного покрытия нужен также с LG, включая
частичную и полную opacity.

## 2. P2: фильтры другого эффекта могут отключить наш материал без fallback

Места: [blur.kcfg](../vendor/kwin-effects-glass/src/blur.kcfg), строка 7;
[blur.cpp](../vendor/kwin-effects-glass/src/blur.cpp), строки 336–337,
413–414, 941–954; [decoration.cpp](../native/decoration.cpp), строки 50–54,
479–481.

Эффект продолжает читать группу `Effect-blurplus` и её whitelist/blacklist.
Старые настройки BlurPlus поэтому влияют на Emerald Glass, хотя его
собственная панель этих фильтров не показывает. При исключении окна
`shouldBlur()` возвращает false, но `egShader` уже установлен в true.
Декорация отключает стандартный blur и, с LG, собственный CPU-материал.
Остаются текст и символы кнопок без ожидаемого стекла.

Проверочная программа использует настоящий `settings.cpp` и сгенерированный
`BlurConfig`: группа `Effect-blurplus` с `BlurMatching=true` и
`WindowClasses=org.kde.dolphin` включает whitelist и исключает
`systemsettings`. Никакие пользовательские настройки для проверки не менялись.
Последствие для handoff следует из приведённых ветвей кода; воспроизведения
этой конфигурации в рабочем KWin не выполнялось.

Нужно изолировать собственные настройки и исключить скрытые фильтры из пути
наших бордеров. Если пропуск отрисовки предусмотрен, handoff обязан возвращать
CPU/standard Blur, а не оставлять `egShader=true`.

## 3. P2: материал не учитывает общую прозрачность окна на KWin 6.7.5

Место: [blur.cpp](../vendor/kwin-effects-glass/src/blur.cpp), строка 1086 и
строки 1361–1362; финальное применение —
[onscreen_rounded.glsl](../vendor/kwin-effects-glass/src/shaders/onscreen_rounded.glsl),
строка 22.

Для модуляции берётся только `data.opacity()`. В используемом KWin 6.7.5
это множитель эффектов, который по умолчанию равен 1; общая прозрачность
окна хранится отдельно. Поэтому при установке прозрачности окна через KWin
рамка LG может остаться полностью непрозрачной, когда клиент и нативные
символы уже прозрачны. Например, при opacity окна 0.5 и data.opacity 1
наш множитель равен 1, а у штатного Blur — 0.25.

Проверено по API и исходникам именно установленной версии:
[WindowPaintData](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/effect/effect.cpp),
[создание paint data](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/scene/workspacescene.cpp),
[штатный Blur](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/plugins/blur/blur.cpp).
Desktop-эксперимент с изменением прозрачности пользовательского окна не проводился.

Нужно учитывать opacity окна с поправкой на поддерживаемую версию KWin;
не переносить формулу между версиями API без проверки.

## 4. P2: CPU-кнопки неактивного окна используют Active tint

Места: [decoration.cpp](../native/decoration.cpp), строки 644–653;
[material.h](../native/material.h), строки 530 и 536.

Вызов передаёт правильный active/inactive accent, но renderer кнопки берёт
`cfg.tint`, не получая текущую tint strength окна. Поэтому Inactive tint не
управляет кнопками неактивного окна, а Active tint неожиданно управляет ими.
Это затрагивает выключенный LG, выгруженный эффект и CPU-снимки при деформации.
В шейдерном пути `egTint` уже выбирается правильно, поэтому материал также
меняется при переходе GPU → CPU.

Воспроизведено на настоящем плагине декорации с тестовым KDecoration bridge:
у неактивного окна Inactive tint оставлен 0%, Active tint изменён с 0 до 200%.
В прямоугольнике кнопки изменились 612 пикселей; её фон и рамка используют
тот же inactive accent. Нужно передавать текущую tint strength в renderer
кнопки, как это уже делается для рамки.

## 5. P2: частичный сбой инициализации GL может подменить материал картинкой фона

Места: [materialpreview.cpp](../native/materialpreview.cpp), строки 87–91,
132–145, 283–285; [decoration.cpp](../native/decoration.cpp), строки 50–54,
326–339.

`m_initialized` становится true до завершения инициализации. Если VAO создан,
но один из shader programs не собрался, первый вызов возвращает пустое
изображение. Следующий вызов пропускает initializeGL, проходит проверку VAO
и возвращает непустой demonstration backdrop при `gpu=false`.

Для grid card `singleFrame` возвращается до CPU-наложения. Декорация считает
любой непустой `m_previewImage` готовым шейдерным материалом и отключает свой
CPU-слой. После ошибки компиляции и следующего изменения размера/настроек
карточка поэтому может показывать сам фон вместо материала и линз кнопок.
`egPreviewMaterial` и `--require-gpu` также ошибочно считают такой результат
успешным GPU-рендером.

Это подтверждённый разбор пути ошибки, а не fault-injection на аппаратном GL.
Нужно отличать успешную инициализацию от попытки, возвращать явный статус
готовности материала и сохранять CPU fallback при неполной инициализации.

## 6. P3: сохранённый ноль оставляет числовую подпись слайдера пустой

Место: [kcm.cpp](../native/kcm.cpp), строки 276–281.

Label заполняется только по `valueChanged`. Если сохранённое значение равно
исходному значению слайдера, например Blur=0, загрузка не вызывает сигнал.
В результате видно `Blurriness:`, но не `0 / 15`. Аналогично для других
контролов с нижней границей 0. Значение и само управление работают.

Воспроизведено загрузкой настоящего KCM в isolated config: Blur=0, тексты
labels в группе — пустая строка и `Blurriness:`. Достаточно инициализировать
label текущим значением при создании строки.

## Отдельный незакрытый дефект: blur восстанавливается только после движения

Пользователь воспроизвёл в Window Decorations:

1. Выбрать Layan и нажать Apply.
2. Снова выбрать Emerald Glass и нажать Apply.
3. Заголовок не получает ожидаемый blur/характер материала.
4. Небольшое перемещение или изменение размера восстанавливает результат.

Это блокирующий для выпуска сценарий P1, но конкретная причина пока не
установлена. Он не считается автоматически следствием пункта 1.

Текущая runtime-проверка через D-Bus показывает:

```text
owned=1 shaderFrames=1 fallbackFrames=0 foreignTracked=0
clientOverlaps=0 rendered=1 blurStrength=7 transformedFrames=0
backdropSaturation=1.73
```

Этот снимок подтверждает регистрацию рамки и создание буферов. Он не доказывает
полноту/свежесть их содержимого и не был синхронизирован с конкретным плохим
кадром. Конфигурация: LG включён, Blur=7, Base Opacity=32%.

Два места требуют направленной трассировки:

- [blur.cpp](../vendor/kwin-effects-glass/src/blur.cpp), строки 379–415,
  437–452, 500–523: область ограничивается текущим `contentsRect` в момент
  событий декорации. Подписка есть на внешнюю геометрию, но нет отдельного
  отслеживания изменения client geometry. В Wayland применение decoration
  state и обновление геометрии — разные стадии commit. Нужно поймать, какой
  snapshot попадает в `data.frame` после смены темы.
- Там же, строки 1147–1191: новые текстуры очищаются, затем копируется только
  dirty region. Нужно установить, получает ли новый кэш полный первый repaint
  сцены под рамкой после смены декорации. Наличие textures не равно валидному
  backdrop. Нельзя лечить это безусловным чтением всего framebuffer вне dirty
  region: так можно снова захватить собственный заголовок и вернуть feedback.

Следующий диагностический шаг: сопоставить идентификатор декорации, её маску,
contents/frame geometry, причины отказа shouldBlur, создание кэша и реально
скопированные регионы до и после движения. После установления причины нужен
регрессионный сценарий смены декорации без дополнительного resize.

Стадии сверены с официальными исходниками KWin 6.7.5:
[применение decoration state](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/xdgshellwindow.cpp),
[client/frame geometry notifications](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/waylandwindow.cpp),
[EffectWindow::contentsRect](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/effect/effectwindow.cpp).
Это основания для диагностики, а не доказательство порядка событий в сбойном
пользовательском запуске.

## Другие замечания перед публикацией

- KCM material preview всегда рисует три правые кнопки и не использует
  `useSystemButtons`; режимы выравнивания 1 и 2 рисуются одинаково.
  [materialpreview.cpp](../native/materialpreview.cpp), строки 99–102,
  233–235, 316–330. Изменение этих настроек не даёт достоверного предпросмотра
  геометрии. Настоящая KDE grid card использует нативную геометрию и является
  отдельным, более точным путём.
- Корневая `.git` в данном workspace — пустой read-only placeholder, полноценного
  корневого Git-репозитория здесь нет. Это ограничение текущей среды; базу и
  полноту будущего release diff проверить нельзя. В `vendor/kwin-effects-glass`
  есть отдельный Git checkout с пятью изменёнными файлами. При оформлении
  репозитория необходимо явно выбрать vendoring или submodule с сохранением
  этих изменений: gitlink на исходный upstream commit их не содержит.
- README не заменяет release-проверку установки из чистого checkout. Нужно
  проверить полный набор зависимостей, выбор декорации, включение собственного
  эффекта при сохранённом стандартном Blur и способ удаления/возврата.
  Текущий installer атомарно заменяет inode каждого .so, но обновление всех
  трёх плагинов одной транзакцией не реализовано.
- `RESEARCH.md` содержит описание старого channel/Snell-профиля как текущей
  архитектуры рамки. Актуальная sheet-модель описана в README и
  `LIQUID_GLASS_REDESIGN.md`; перед публикацией архитектурное описание нужно
  согласовать. Исторические результаты можно сохранить с явным статусом.

EGL-проверки выполнялись на llvmpipe. Автоматический grid-card тест использует
реальный KDE PreviewBridge, но software Qt Quick и не требует успешного GPU
материала. Текущие 4/4 не проверяют работу BlurEffect целиком в compositor,
переход Layan → Emerald, фактическую валидность backdrop-кэша, аппаратный
GPU, несколько масштабов/экранов или стоимость реального desktop frame.

Изолированный compositor запустить в sandbox не удалось: создание нового
D-Bus socket запрещено. Это не мешало read-only запросам к уже существующей
пользовательской сессии отдельными разрешёнными командами qdbus6.

Для приёмки сначала закрыть сценарий смены темы и потерю alpha в LG, затем
дефекты параметров и fallback. Зелёные штатные тесты сами по себе не являются
основанием считать эти пункты исправленными.
